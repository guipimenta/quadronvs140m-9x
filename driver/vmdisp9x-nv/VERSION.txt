3038: M4.3 NATIVE MEMORY SETUP (first M4 item after E4). CONFIRMED ON THE T61
2026-10-22: PFB reports 128 MB (cfg0 01001800 cfg1 01449000), window 24 MB,
layout OK, native 1024x768x32 desktop unchanged.
 - The scanout window handed to the shadow blitter is no longer a fixed 12 MB:
   it is min(VRAMLimit MB, PCI BAR1 size, NVFB_WINDOW_MAX=24 MB), i.e. 24 MB
   by default, which leaves room for three 1024x768x32 flip buffers.
 - NV_vram_check() (vxd_nv.c) reads the real VRAM size from PFB 0x10020C
   (nouveau nv50_vram.c decode) plus PFB cfg0/cfg1, and validates the layout
   in nv50_evo.h: window < EVO reservation (24 MB), VRAM >= 32 MB + 32 KiB
   (RAMIN end). It runs in LIVE VM context only (first call from the
   mini-VDD register handler, i.e. DriverInit; also lazily before any native
   mode set) because BAR0 access inside Device_Init freezes the G86.
 - NV_native_modeset refuses to run if the check failed, so a wrong card or
   layout logs a reason instead of scribbling EVO structures into VRAM.
 - nvprobe (no arguments) now prints VRAM size, cfg regs, window and the
   check result; 'nvprobe log' shows the NV_vram_check lines.

3037: *** ROOT CAUSE OF EVERY 'LoadFail = nvmini.drv 0000' SINCE M1 - FIXED ***
CONFIRMED ON THE T61 2026-10-22: LoadSuccess = nvmini.drv, native EVO modeset
1024x768x32 at boot, desktop usable, Display Properties can change depth.
nvmini.drv never ran: Win98 KERNEL rejected the NE image before calling
DriverInit. init.c declared `extern char __based(__segname("_TEXT")) *pText`
and locked (__segment)pText. Current Open Watcom compilers treat "_TEXT" in
__segname() as a user DATA segment: they emit an empty FAR_DATA segment named
_TEXT, wlink drops it, and the .drv keeps a SEGMENT relocation to non-existent
segment 3 (see tools: `python3 -I <scratch>/nerelocs.py nvmini.drv`). The
loader fails the fixup -> LoadModule error 0 -> vga.drv. Upstream's 2023-era
toolchain did not do this, which is why the official release loads.
Fix: GlobalSmartPageLock(get_cs()) with `#pragma aux get_cs = "mov ax,cs"`.
Proven in a QEMU Win98SE harness: with the fix, vesamini.drv (same 16-bit
objects) logs 'D> DriverInit: ENTER', connects to the VxD, and brings up a
1024x768x16 desktop. Also in 3037: the 16-bit driver is linked with the
2025-08 Open Watcom (the Oct-2026 wlink snapshot ignores 'segment type data
preload fixed'; the makefile now also names class DATA/BSS explicitly), the
DIBENG mini driver's NE now matches the official layout (flags 8201, FIXED
DGROUP, no data-segment entries). dbg output additionally mirrored to I/O
port E9h (QEMU -debugcon), harmless on real hardware.

3031: THE DRIVERINIT FIX (from Win98SE VDD.VXD disassembly, 98 DDK symbols).
The Win98 VDD keys every display-driver call on EBX as a DISPLAY DEVICE ID
(1..N), not a VM handle. Id 1 = the devnode the VDD considers "the VGA" and
is served by the global mini-VDD dispatch table. A mini-VDD the VDD loads for
any OTHER display devnode is moved into that device's private table and the
global table is restored (VDD _LoadMiniVDD). The upstream vmdisp9x .drv
always registers with EBX = VM id = 1, so on this T61 - where the ghost
"Standard PCI Graphics Adapter (VGA)" is id 1 and the NVIDIA devnode is id 2 -
the register call hit an empty table, EDX stayed 0, DriverInit returned 0.
nvmini.drv now tries VDD_REGISTER_DISPLAY_DRIVER_INFO with ids 1..4 and keeps
the first id whose mini-VDD returns an FBHDA alias for all later VDD calls.
The VxD logs that id right after the 0x300 marker (slot [1]).

3030: boot-handshake VRAM trace. With display.drv=nvmini.drv the 16-bit driver

  2. reboot (Native=1) -> it falls back to vga.drv as before

       (absent/all-zero -> handshake dies BEFORE our mini-VDD)

     vram_pm16 selectors.
